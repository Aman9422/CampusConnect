## 🆕 v8.5.0 — Teacher Dashboard Analytics Data Not Showing

**Symptom (device log):** the teacher dashboard showed zeros for resume review insight, review analytics, placement prediction, institute skill gap and performance trend, while Department Overview / Quick Stats / At-Risk worked. The provider log line proved the discrepancy:
`TeacherAnalyticsProvider: Loaded 0 reviews, 0 students, 1 depts, 1 pipeline eligible, 1 engagement summaries`.

**Root cause 1 — `getStudentResumeData()` skipped every student without a `resumeReviews` doc.** The loop did `if (latestReview == null) continue;`, so the only student in this database (role=student, present in the dept/pipeline/engagement queries that found "1") was dropped from the leaderboard. Every review-sourced section (`studentData`, placement prediction indicators via `getPlacementPredictionIndicators`, at-risk detection, and the "Students" count feeding Quick Stats / AI Insights / AI Summary) is built on this list — hence "resume review insight, review analytics, placement prediction indicator" showing nothing despite a student existing. Fix: un-reviewed students now enter `studentData` with `latestScore: 0` and `reviewCount: 0` (consistent with pipeline/dept/engagement counts and flagged by the at-risk "No resume reviews" signal).

**Root cause 2 — brittle ATS-score/date extraction.** `_extractScore` was `data['atsScore'] as int? ?? -1` — a single `double`/string score (console edits / legacy writers) throws `TypeError`, and since `getResumeReviewStats` maps over **all** reviews, one malformed doc zeroes the entire review-analytics section. `_extractDate` only accepted Timestamps, so legacy ISO-string dates were lost (blanking performance trends month keys). Fix: `num` coercion with `clamp(0,100)`, legacy `ats_score` string parse, and Timestamp→ISO-string fallbacks.

**Non-issue (deploy-proven): `resumeReviews.createdAt` index is auto-provisioned.** `getPerformanceTrendInsights` runs `collectionGroup('resumeReviews').where('createdAt', >=, ...)`. An explicit single-field collection-group index was initially added to `firestore.indexes.json`, but the first `firebase deploy --only firestore:indexes` rejected it with HTTP 400 *"this index is not necessary, configure using single field index controls"* — this database runs in **index-management mode**, where single-field collection-group indexes are auto-provisioned and must NOT be declared in the indexes file. The entry was reverted and the deploy then completed: **`Deploy complete!`** — so no index work is required for the performance-trend query.

**Portfolio audit (requested):** reviewed the v8.4.9 (MB17 `_extractPortfolioMap`/`_unflattenPaths` + MB18 `backfillEmail`) implementation for mistakes — **none found**. The read is tolerant of both nested and flattened shapes; the email backfill is uid-scoped, once-per-user and non-fatal; portfolio writes self-heal to the canonical nested shape.

## ✅ v8.4.9 — Flattened-Shape Portfolio Read Fix + Email Backfill

The v8.4.8 device log is **conclusive**: the MB13 diagnostic fired as
`PortfolioService.getPortfolio: doc USERS/SWJLWtNNV7RMnhmcUquXTmW2mfH3 EXISTS but portfolio key is MISSING. Doc keys present: (isPublicProfile, career, metadata, ..., portfolio.certifications, metadata.updatedAt)`.
The doc has **no nested `portfolio` map** — every portfolio section is stored as a **root-level key whose name contains dots** (`portfolio.resume`, `portfolio.projects`, `portfolio.certifications`, …) — the signature of Firebase-console JSON edits / legacy writers. The reader looked up `data['portfolio']`, so it saw nothing while the console clearly held all the data: **this is the exact mechanism behind Symptom 1 ("console has data, app shows empty")**. The user's own console dump (uid `SWJLWtNNV7RMnhmcUquXTmW2mfH3`) confirms resume + projects + experience + certifications + achievements + languages + preferences are all present — so UID mismatch, wiped doc, and parsing are all ruled out. The reader simply looked in the wrong shape.

- [x] **MB17 — Tolerant read of flattened `portfolio.*` keys** (`lib/services/firestore/portfolio_service.dart`) — new `_extractPortfolioMap(data)` used by BOTH `getPortfolio` and `portfolioStream`: returns the nested `portfolio` map when present; otherwise rebuilds a portfolio map from any root-level `portfolio.<section>` keys via `_unflattenPaths` (deeper leaf-flattened keys like `portfolio.resume.downloadUrl` are re-nested under their section); otherwise null → empty. A doc with flattened keys (the confirmed root cause — the device log showed "portfolio key is MISSING … keys present: …, portfolio.certifications, …") now parses to the real portfolio instead of empty. The MB13 diagnostic still fires only when neither shape carries a portfolio. (Symptom 1 root fix)
- [x] **MB18 — Backfill blank `personal.email`** (`lib/services/firestore/profile_service.dart` + `lib/providers/profile_provider.dart`) — the console dump showed `personal.email: ""` because the doc predates the denormalized field / an older write blanked it (not a feature; the setup screen renders email read-only from this field). New `ProfileService.backfillEmail` performs a targeted `personal.email` merge (portfolio + everything else untouched) when the stored value is blank; `ProfileProvider.initWithUser` calls it once per user (`_emailBackfillUid`, cleared on `reset()`), non-fatal on failure, and mirrors the email into memory so the setup/edit screens show it immediately.
- [x] **MB19 — Validation** — `flutter analyze`: **No issues found** on all 3 changed files (`portfolio_service.dart`, `profile_service.dart`, `profile_provider.dart`); `flutter test`: **all 65 tests passed**. ## ✅ v8.4.8 — Portfolio Read Failure & Refresh-Wipe Fix

Two user-reported symptoms: (1) console shows `users/{uid}/portfolio` data but the app renders an empty portfolio at 10% strength with "No Resume"; (2) upload → visible → pull-to-refresh → wiped back to "No Resume". The tolerant `fromMap` layer (v8.4.7) proves parsing can't throw; the code-verifiable bugs are in the **read-apply logic** of `PortfolioProvider` — two of the three read paths blindly overwrite memory with whatever the server returns, including an empty result. Only the stream listener has the v8.4.4 stale-guards.

- [x] **MB11 — Stale-guards in `PortfolioProvider.refresh()`** (`lib/providers/portfolio_provider.dart`) — `refresh()` did `_portfolio = fresh` + `_cacheService.cache(...)` **unconditionally**; a single empty `getPortfolio()` (doc missing / `portfolio` key missing / transient failure) wiped a just-uploaded resume from memory AND overwrote the SharedPreferences cache with the empty result (exact mechanism of Symptom 2). Now applies the same three guards as `_listenToPortfolio`: (1) skips if a local write is in flight (`_isUploadingResume || _isSaving`), (2) never lets an empty `fresh` wipe a non-empty `_portfolio`, (3) never lets `fresh` drop the resume while memory still has one. Keeps last-known-good on error; only re-caches when the fresh value actually replaces memory. (Finding 1)
- [x] **MB12 — `initWithUser` inner catch must set `_error`** (`lib/providers/portfolio_provider.dart`) — the one-shot-get `catch` did `_portfolio ??= PortfolioModel.empty()` **without** setting `_error`, so a failed startup read rendered as "a newly initiated portfolio at 10% strength" with no banner — Symptom 1's exact UI (the v8.4.7 error banner exists but this path never triggered it). Now sets `_error = 'Failed to load portfolio'` when falling back to empty; also removed the `_error = null` that ran after `_isInitialized = true` (it would have swallowed the banner) — the stream listener clears the error once a real event arrives. (Finding 2)
- [x] **MB13 — Diagnostic in `PortfolioService.getPortfolio`** (`lib/services/firestore/portfolio_service.dart`) — when the doc exists but `data['portfolio']` is null, `debugPrint` the uid + presence of the `portfolio` key so a single debug run distinguishes UID mismatch (console doc ≠ logged-in account, candidate A) from a wiped doc (candidates B/C). Also hardened the `portfolio` read with a type check (`is! Map<String, dynamic>` → log + empty) so a malformed field degrades gracefully instead of throwing a `TypeError`. (Finding 4)
- [x] **MB14 — Guard `createProfile` against silently wiping an existing portfolio** (`lib/services/firestore/profile_service.dart`) — `createProfile` did `doc(uid).set(profile.toFirestore())` with **no merge**; if it ever ran on an existing doc (role/setup re-entry race with `initializeProfile`'s `exists` check) it overwrote the whole document including `portfolio`. Now re-checks doc existence itself: fresh doc → full `set` (initial creation); existing doc → `SetOptions(merge: true)` so `portfolio` and any sections not in `StudentProfile.toFirestore()` are preserved. (Finding 4B)
- [x] **MB15 — `ResumeSummaryCard` surfaces the error state** (`lib/widgets/resume_summary_card.dart`, `lib/views/dashboards/student_dashboard_view.dart`) — the card only received `portfolio?.resume` and ignored `provider.error`, so a failed load silently masqueraded as a fresh (empty) portfolio on the dashboard. The card now takes an `error` param and renders a red banner (error icon + message) above the status row; the dashboard passes `portfolioProvider.error` through. (Finding 4/Recommended fix 5)
- [x] **MB16 — Validation** — `flutter analyze`: **No issues found** on all 5 changed files (`portfolio_provider.dart`, `portfolio_service.dart`, `profile_service.dart`, `resume_summary_card.dart`, `student_dashboard_view.dart`). `flutter test`: **all 65 tests passed**. `flutter test` runner count went 58 → 65 (three new sub-suites contributed more cases / re-counted).
- [x] **User-side verification (completed 2026-08-07)** — Firebase console dump for `users/SWJLWtNNV7RMnhmcUquXTmW2mfH3` confirms the portfolio data lives under the **logged-in uid**: `portfolio.resume` (downloadUrl + storagePath `resumes/SWJLWtNNV7RMnhmcUquXTmW2mfH3/latest.pdf`, fileSize 186465, version 1, uploadedAt 22:06:27), `portfolio.projects`, `portfolio.experience`, `portfolio.certifications`, `portfolio.achievements`, `portfolio.languages`, `portfolio.preferences` — plus `role: "student"`, `academic` (JDCOEM/CSE/8.9), `profileCompleted: true`. **Candidate A (UID mismatch) RULED OUT**; **candidate C (canceled-upload metadata write) RULED OUT** (resume metadata fully landed); **candidate B (createProfile wipe) RULED OUT** (doc intact, MB14 guard in place). With this data the screen renders at **~80% strength** (resume 20 + projects 20 + experience 10 + certifications 15 + achievements 5 + education 10) — not the 10% education-only state. Note: `portfolio.skills` / `portfolio.links` were never written (only root-level `skills` string list exists), so those two sections correctly stay hidden — data-entry observation, not a bug. **Remaining step is a device rebuild/re-run** — a stale debug build running the pre-fix `refresh()`/init logic can still exhibit the old symptom; the MB13/error-banner paths surface any genuine remaining read failure.
